# rubash-as-engine: the embeddable Session API (detailed RFC for #595)

Status: **FINAL — approved by the owner on 2026-10-25.** Document version:
final (2026-10-25), superseding the review draft of the same date. All
questions in §11 are decided (per the recommendations recorded there; the
decision record is §12). This document is the detailed API RFC that
Pillar 2 of the 1.5.0 RFC (`docs/design/1.5.0-workspace-and-engine-api.md`)
calls for: that document fixes the release shape (four-layer workspace,
stability boundary, train); this one designs the actual embeddable surface —
session, execution, injection, callbacks — from the only two sources of truth
we have: the engine's current public face, and the call patterns of its first
real consumer, niubash. Nothing here changes code; it freezes a design for
implementation. It is finalized together with the native-debugger design
(#497) as one 1.5.0 implementation program: the workspace split proceeds
module by module, and each module's debug hooks land on the seams the split
creates.

Version facts this document is written against: engine `1.4.3`
(rubash master `1e72c7f9`), niubash master `b53e6bff`, niubash's release pin
at engine rev `4c41e2c0` / version `1.4.3`
(`niubash/scripts/release/rubash-pin.json`). The 1.4.1–1.4.3 slots of the
RFC-v1 train have shipped; the layer split has not started.

---

## 1. Problem statement

rubash is already consumed as a library. niubash links it, drives its
executor, implements its history trait, calls its parser for its own
features, and builds its REPL on the driver's interactive helpers. An
editor-class host — a program that wants a real shell session inside its own
process, with its own rendering, input, and lifetime — is the stated 1.5.0
target. But what exists today is not an API; it is the engine's internals,
public by accident of the single-crate layout:

- **Everything is public.** `src/lib.rs` exports 20 modules wholesale
  (`executor`, `parser`, `lexer`, `shell`, `builtins`, `jobs`, …) plus five
  convenience re-exports. There is no line between "contract" and
  "implementation", so every internal refactor is a potential downstream
  break, and nobody can say which breaks matter.
- **The de-facto host API is an accretion, not a design.** The methods a host
  actually uses live in `src/executor/public_accessors.rs` (~2,000 lines of
  `pub fn` on `Executor`), in free functions in `src/script_driver.rs`
  (5,000+ lines: `run_source`, `run_stdin_script`,
  `pre_process_interactive_line`, `stdin_source_needs_more`, …), and in
  module paths like `shell::bind_registry` and `builtins::kill` that were
  never meant as surface.
- **Internal types leak into signatures.** `Executor::shell_state()` hands
  out `&ShellState` / `&mut ShellState`; `run_source` and friends traffic in
  the raw executor; parser entry points return the internal `Ast` /
  `CommandNode`. Freezing today's face as-is would freeze the engine's
  internal data model with it.
- **The consumer's real call patterns are invisible to the design.** A census
  of niubash's call sites (see §3) shows the host lives on a small set of
  operations — environment writes dominate (55 `set_env` call sites),
  followed by option setting (22 `set_shell_option`, 7 `set_shopt_option`),
  exit-code reads (11), plus one each of history-provider injection and
  completion. None of these is a named, grouped, documented operation today;
  each is one method among hundreds.
- **Versioning is already drifting in practice.** niubash's `Cargo.toml`
  declares `rubash = { version = "1.4.1", git = …, branch = "master" }` —
  the version field is fiction; what actually pins the engine is a separate
  release mechanism (a JSON pin + a `[patch]` path override). There is no
  semver contract for the number to refer to, no MSRV commitment beyond the
  `rust-version = "1.70"` field, and no API changelog.
- **We have already broken the consumer once without noticing.** In a recent
  bulk merge, a `builtins::kill` helper that niubash's Ctrl-C handling calls
  silently vanished from the engine; niubash master stopped compiling until
  it was restored (tracked as its own regression issue). The helper was
  never API — but the consumer depended on it, and nothing in our process
  knew. That is the cost of an unowned surface, paid once already.

The gap, restated: rubash needs a **session-level** API — one designed
object that owns a shell session, takes input, emits output and events,
accepts injected state and host services, and carries an explicit stability
promise — with everything else demoted to explicitly-unstable internals.

## 2. Goals and non-goals

### Goals

1. A host can embed a full GNU-semantics shell session using **only** the
   documented stable surface: create a session, feed it source, receive its
   output and lifecycle events, inject variables/fds/services, interrupt it,
   and close it — without naming any internal module.
2. niubash's every current call pattern is expressible on the stable surface
   or on a named, tracked migration path off it. niubash is the
   compatibility baseline: if the API cannot serve niubash, it is wrong.
3. Stability is **tiered and mechanical**: each public item belongs to a
   tier with a written change policy, and CI can tell which tier a change
   touches.
4. The engine keeps its differentiator: semantics stay GNU-pinned by the
   golden corpus at every tier; the API exposes that fidelity (structured
   diagnostics, real exit/signal status), it does not sand it down to a
   lowest common denominator.

### Non-goals

- **Not a redesign of execution.** The executor, parser, and variable model
  stay as they are; this RFC draws a boundary around them.
- **Not a C/FFI ABI in 1.5.0.** The contract is a Rust API. (The design
  avoids Rust-only exotica in the stable tier so a future ABI is not
  foreclosed, but no ABI is promised.)
- **Not async.** Both real consumers drive the engine synchronously today;
  the stable API is synchronous (see Q1).
- **Not the interactive layer.** Line editing, prompt rendering, and
  terminal ownership stay in the interactive layer and in hosts. The engine
  exposes the *hooks* an interactive layer needs; it does not grow one.
- **Not the debugger.** The 1.5.0 debugger is a sibling design; it will
  consume this API (breakpoints need the event surface). Its decision
  points are settled in that design — finalized 2026-10-25, together
  with this RFC, as one implementation program.

## 3. Where we are: the current surface, inventoried

### 3.1 What the crate exports today

- 20 public modules (full list in `src/lib.rs`), no `#[doc(hidden)]`
  separation, no feature gates.
- Root re-exports: `Executor`, `ExecuteError`, `Token`/`TokenKind`,
  `Ast`/`CommandNode`/`Redirect`, `decode_to_visible_text`, and (Windows)
  the elevation trio.
- `Executor` itself: fields are private/`pub(crate)` (good), but its public
  method set is spread across dozens of `impl` blocks; the host-relevant
  subset concentrates in `public_accessors.rs`.
- `script_driver` free functions form a second, parallel API at driver
  level: `run_script_with_history*` (4 variants), `run_source*`,
  `run_stdin_script`, `run_interactive_stdin`, `pre_process_interactive_line`
  (returning `InteractiveExpansion`), the `stdin_source_needs_more*` family,
  and history/console bind helpers (`initialize_interactive_history`,
  `bind_interactive_console_winsize`, …).

### 3.2 What niubash actually consumes (the compatibility baseline)

Census of `rubash::` references in niubash master (`crates/niubash-runtime`
+ `src/main.rs`):

| Surface | Items | Notes |
| --- | --- | --- |
| `executor::{Executor, ExecuteError}` | core | the object niu drives directly |
| `Executor` methods | `set_env` ×55, `set_shell_option` ×22, `last_exit_code` ×11, `set_shopt_option` ×7, `inherit_process_stdin` ×5, `set_history_provider` ×1, `complete_line` ×1 | the host's working set |
| `history::HistoryProvider` | trait impl + `SharedHistoryProvider` injection | the one true capability trait today; the pattern to generalize |
| `script_driver` | `run_source_with_line_offset`, `run_stdin_script`, `run_script_with_history*`, `run_interactive_stdin`, `pre_process_interactive_line`, `prepare_interactive_history`, `script_uses_history/aliases`, `check_binary_file`, `heredoc_delimiter_unclosed_quote` | driver + REPL plumbing |
| `parser` | `parse`, `parse_with_options`, `CommandNode`, `ParseLoopOptions`, `WordMetadata`, `ast_print::pretty_print_command` | used for niu's own parse-aware features |
| `lexer` | `tokenize`, `tokenize_with_initial_posix`, `has_unclosed_input_syntax*` | continuation/completeness checks |
| `shell::bind_registry` | `BindEntry`, `BindKind::{Execute, Function, Macro}` (20 refs) | keybinding registry — internal by design, consumed anyway |
| `invocation` | 5 refs incl. `materialize_command_file` | startup plumbing |
| `usage` | help/version printers (6+) | the shared host/engine printer — already a deliberate bridge |
| root + misc | `decode_to_visible_text`, `executor::shell_pwd_display_path` | display helpers |
| `builtins::kill` | `note_console_ctrl_c`, `consume_background_wrapper_handshake` | internal hooks; one of these disappearing is what broke niu master in the bulk-merge incident |

Three conclusions fall out of the census:

1. **The working set is small.** ~15 operations cover the overwhelming
   majority of host interactions. A designed API can put exactly these
   first, instead of exposing ~200 methods and hoping.
2. **The long tail is real and must be owned.** bind registry, invocation
   plumbing, kill hooks: niu needs them today. The migration path (§8) must
   give each a home — a stable equivalent, a tier-B helper, or an explicitly
   unstable internals gate — not a shrug.
3. **The trait pattern already works.** `HistoryProvider`
   (`Rc<RefCell<dyn HistoryProvider>>`, injected via `set_history_provider`)
   is in production and uncontroversial. Host services in the new API are
   generalizations of it, not inventions.

### 3.3 Process-global hazards the API must fence off

`Executor` carries process-level semantics a library must not spring on a
host: a drop-time process-environment restore (skipped only for the
designated process-exit executor), signal-mailbox ownership, and
console-control hooks. The Session API must make process-global effects
**opt-in and documented** (a session is inert to the process unless the
host asks for the process-exit role), because an editor embedding three
sessions must never have one of them rewriting the process environment on
drop.

## 4. Design principles

Derived from the census and the one production embedding:

1. **The session is the unit.** Hosts think in sessions (one per REPL pane,
   task runner, or editor buffer), not in executors-plus-free-functions.
   Everything a host needs hangs off one object with one lifetime.
2. **Make the census operations first-class.** Environment writes, option
   setting, exit-status reads, history injection, completion: these get
   named, grouped methods — not scavenger hunts through `public_accessors`.
3. **Services in, events out.** Things the host *provides* (history,
   completion backing, rc policy, external-command handling) are capability
   traits injected at build time, generalizing `HistoryProvider`. Things the
   host *observes* flow through one event-observer trait (§7).
4. **Values at the boundary, internals inside.** Boundary types are owned,
   plain data (`String`, `Vec`, small structs/enums marked
   `#[non_exhaustive]` where they will grow). No `&ShellState`, no raw
   `Ast`, no `Rc<RefCell<…>>` in stable signatures except where a capability
   trait's shared handle already established the pattern.
5. **Synchronous, single-threaded, honest about it.** A `Session` is used
   from one thread at a time (the current executor model, including the
   `Rc<RefCell>` history handle, already assumes this). The API says so in
   its contract instead of letting hosts discover it.
6. **Process-global effects are opt-in.** Environment restore on drop,
   signal mailbox ownership, console hooks: default off for library
   sessions; the process-exit role is an explicit builder flag (§5.1).
7. **Every stable item has a GNU anchor.** Where the API exposes semantics
   (exit statuses, signal deaths, diagnostics wording), the semantics are
   the golden-pinned ones; the API's job is faithful delivery, not
   reinterpretation.

## 5. The API, layer by layer

All names below are design sketches, not final signatures. The stable tier
lives in a single module — `rubash_core::api` after the workspace split
(until then, `rubash::api` in the facade crate) — so "is it contract?" is a
question `cargo` path layout answers, not a wiki page.

### 5.0 Layer 0: the workspace crates (from RFC v1, restated)

`rubash-core` (engine; no terminal, no platform windowing deps) carries the
stable tier. `rubash-driver` carries tier-B driving helpers.
`rubash-interactive` carries the fast-moving interactive layer.
`rubash` (facade) re-exports and keeps niubash's "one crate" import shape
during migration. The dependency direction is CI-pinned, per RFC v1.

### 5.1 Layer 1: session lifecycle

```rust
let mut session = Session::builder()
    .environment(initial_vars)          // instead of 55 post-hoc set_env calls
    .working_directory(path)
    .argv0(name)                        // $0 / diagnostic prefix identity
    .history_provider(provider)         // capability: §5.5
    .external_command_handler(handler)  // capability: §5.5
    .events(observer)                   // §5.6
    .process_exit_role(false)           // default: library-inert (§3.3)
    .build()?;
```

- `SessionBuilder` with consuming setters and a fallible `build()` —
  startup can fail (bad cwd, bad provider) and hosts deserve a `Result`,
  not a half-initialized executor.
- `Session::close(self) -> i32` runs the exit path (EXIT trap, logout file
  rules) and returns the final status; dropping without `close` is defined
  (no traps, no process effects) so hosts that forget still behave sanely.
- Multiple sessions per process are supported and independent, except for
  documented process-global resources (signal mailbox), where the API
  defines arbitration: the first session to enable kernel signal delivery
  owns it; others get job-control-free delivery. (Today this is implicit;
  this RFC makes it a written rule — the threading contract is decided in
  §11 Q5.)

### 5.2 Layer 2: execution

```rust
pub struct RunOptions {
    pub source_name: Option<String>,   // diagnostic prefix / $0-ish identity
    pub line_offset: usize,            // REPL hosts submit line-by-line
    pub interactive: bool,             // history recording, alias gates, job notices
    pub capture: Capture,              // inherit session streams | capture output
}
pub struct RunOutcome {
    pub status: i32,                   // includes 128+sig for signal deaths
    pub flow: Flow,                    // Completed | ExitRequested(i32) | Return(i32)
    pub diagnostics: Vec<Diagnostic>,  // structured, §6.3
}
session.run(source, &RunOptions) -> Result<RunOutcome, SessionError>
session.run_line(line) -> Result<RunOutcome, SessionError>   // interactive-shaped sugar
session.parse(source) -> Result<ParsedUnit, ParseFailure>     // no execution
session.expand_word(word) -> Result<String, SessionError>     // expansion-only helpers
session.call_function(name, args) -> Result<i32, SessionError>
```

- `run_source`, `run_script_with_history*`, `run_stdin_script`,
  `run_interactive_stdin` collapse into `run` with options. The four
  history-flavored `run_script_*` variants exist because history behavior
  was a parameter the signature couldn't hold; `RunOptions` holds it.
- `flow` makes the `exit` builtin a *value the host acts on* instead of a
  process event: an embedding host decides whether `exit` closes the
  session, the pane, or nothing. (Today this leaks through exit-jump flags
  the host must know to poll — `take_exit_jump_pending` is exactly the kind
  of mechanism the API replaces with a return value.)
- `parse` serves hosts that pre-validate or render structure; the returned
  unit is the tier-B syntax surface (Q4), not the internal `Ast`.

### 5.3 Layer 3: state injection and inspection

Grouped, named, and symmetric — the formalization of the census's top rows:

```rust
session.variables()  -> VariableView    // get / set / export / unset / attributes
session.variables().set_array(name, cells) / .get_array(name)
session.options()    -> OptionView      // set -o by name, shopt by name, with validity
session.environment() -> process-env delta view (what children will inherit)
session.cwd() / session.set_cwd(path)
session.positional() / session.set_positional(args)
session.aliases() / session.functions() // snapshot + define/undefine
session.last_status() -> i32            // the ×11 call, named plainly
```

Rules: stringly-typed names stay (that is shell), but validity is checked
and reported (`set_shopt_option` already returns `bool` — the API keeps
that honesty everywhere); snapshots return owned data; array access goes
through the typed-cell view so hosts never touch the mirror encoding.

### 5.4 Layer 4: input, output, and file descriptors

- **Standard streams are traits at the boundary.** A session is built with
  an input source and two output sinks:
  `input: impl Read`-shaped source for non-interactive feeding, and
  `out`/`err` byte sinks with explicit flush points. The default is
  "inherit the process streams"; an editor host substitutes in-memory
  sinks and gets every byte, including builtin output — output takeover is
  total or it is worthless.
- **Prompt output is a separate channel.** Prompt strings are produced via
  `expand_prompt` and delivered through the event observer (§5.6), never
  interleaved into the command-output sink; a host renders prompts itself.
- **fd 0/1/2 are injectable; the fd table is not exposed.** A host may bind
  the session's standard descriptors to its own handles/files at build time
  (the formal version of today's `inherit_process_stdin` and the driver's
  console-size bind helpers — resize becomes `session.notify_terminal_size(cols, rows)`).
  Numbered fds beyond 2 stay engine-internal in 1.5.0 (Q6).
- **External commands** spawn through the session's stream bindings by
  default; the host's external-command handler (§5.5) can intercept —
  formalizing `set_host_external_command_handler`, which niu already uses
  to route commands.

### 5.5 Layer 5: host services (capability traits)

Injected at build time; each generalizes a mechanism that exists today:

| Capability | Formalizes | Shape |
| --- | --- | --- |
| `HistoryProvider` | exists verbatim | keep; move to tier A unchanged if possible |
| `ExternalCommandHandler` | `set_host_external_command_handler` | decide/run-or-delegate for non-builtin commands |
| `ElevationHandler` | `set_elevation_handler` | sudo/elevation requests as data |
| `CompletionProvider` | backing for `complete_line` | host commands the engine cannot know |
| `RcPolicy` | #359 plan-A bridge (RFC v1 pillar 3) | host decides profile/rc sourcing per session |
| `DiagnosticSink` | today's stderr text + prefix helpers | receives `Diagnostic` values (§6.3) |

Capability traits return data or decisions; they are the only places a host
can alter execution, and each alteration point is documented per trait.

### 5.6 Events (observer)

One observer trait, default no-op methods, registered on the builder:

```rust
pub trait SessionEvents {
    fn before_command(&mut self, _e: &CommandEvent) {}
    fn after_command(&mut self, _e: &CommandEvent, _status: i32, _elapsed: Duration) {}
    fn cwd_changed(&mut self, _new: &Path) {}
    fn exported_variable_changed(&mut self, _name: &str, _value: Option<&str>) {}
    fn prompt_ready(&mut self, _prompt: &str) {}
    fn exit_requested(&mut self, _status: i32) {}
    fn job_status_changed(&mut self, _job: &JobInfo) {}
}
```

Events are notifications, not control flow — an observer cannot veto a
command. The two historical exceptions stay where they already live as
capabilities, not events: history recording veto (inside the interactive
line path, cf. today's `interactive_history_veto_recording`) and rc policy.
Job events formalize the completion notices shells print and hosts
currently scrape from output text.

## 6. The consumer's perspective: the hooks a host actually needs

This section is written from the integrating host's chair. Each hook is
stated as the host's need, then the API answer, then the current mechanism
it replaces.

### 6.1 Output streams

*Need.* "Give me every byte the session prints, on the channel it belongs
to, and tell me when a command's output is complete so I can fold, copy, or
index it." Partial capture is the classic embedding failure: builtins write
to one place, children to another, prompts to a third.

*Answer.* §5.4's sink takeover is total: builtin output, child stdio
(bindings inherited), diagnostics (also as values, §6.3), and prompts
(separate channel). `after_command` is the completion boundary. Capture
mode (`Capture::Capture`) gives `run` a per-call output bundle for
task-runner hosts that don't want streams at all.

*Replaces.* Ad-hoc fd plumbing plus output scraping; the driver's habit of
writing to the process's real stdout regardless of who owns the executor.

### 6.2 Completion

*Need.* "The user pressed Tab in my editor. Give me candidates for this
line and cursor, including commands only I know about, and respect the
session's compspecs."

*Answer.* `session.complete(line, cursor) -> Vec<Candidate>` (structured:
text + optional description), promoted from today's
`Executor::complete_line(line, cursor) -> Vec<String>`; compspec
registration/inspection on the session; a `CompletionProvider` capability
(§5.5) the engine consults for host-registered commands, with the engine's
own programmable-completion semantics (the COMP_* protocol) intact for
shell-level functions.

*Replaces.* `complete_line` + `has_compspec` scattered on the executor, and
the host having no sanctioned way to add its own commands to the candidate
space.

### 6.3 Diagnostics

*Need.* "Don't make me parse stderr text to put a squiggle on line 3.
Give me the diagnostic as data: message, source name, line, kind — and keep
printing the GNU-identical text form to the error sink for terminal hosts."

*Answer.*
```rust
pub struct Diagnostic {
    pub kind: DiagnosticKind,        // Parse | Runtime | Builtin | Expansion
    pub message: String,             // the GNU-worded message
    pub source_name: Option<String>,
    pub line: Option<usize>,
    pub status: Option<i32>,         // exit status the diagnostic carried, if any
}
```
Delivered twice: as text (unchanged wording — the goldens pin it) to the
error sink, and as values in `RunOutcome::diagnostics` and to the
`DiagnosticSink` capability for streaming cases. Parse failures from
`session.parse` carry span information from the syntax layer.

*Replaces.* The five `diagnostic_prefix*` / `error_prefix*` helper families
on the executor — hosts today must reconstruct after the fact what the
engine knew when it printed.

### 6.4 Cancellation and signals

*Need.* "The user hit Ctrl-C / closed the pane / the task timed out.
Stop the current command promptly, leave the session usable, and tell me
whether it died by signal."

*Answer.* Two mechanisms, because hosts have two different intents:
- `session.interrupt()` — cooperative cancellation: the executor checks
  the flag at command boundaries and at the same points the console
  interrupt path is honored today; the running command ends as if SIGINT
  had arrived (status 130, traps honored), and the session continues.
- `session.inject_signal(sig)` — parity with an external signal: queues the
  signal through the same delivery machinery as `kill` to the shell's own
  pid, so trap behavior is identical to the terminal case, including for
  the fatal pair whose handlers the engine always installs.
Signal deaths surface in `RunOutcome.status` as 128+sig and in
`after_command`, never as ambiguity.

*Replaces.* The console-Ctrl-C internal hooks niu calls today
(`builtins::kill` functions) — the exact surface that broke niu master when
it vanished. Under this RFC those become tier-C internals with a stable
equivalent, and the canary (§8) fails CI if the stable equivalent moves.

### 6.5 Input injection and completeness

*Need.* "I feed the session programmatically — a REPL line, a task script,
a here-doc assembled by the user. I need to know if the input is complete
or whether I should show a continuation prompt, and I need line numbers in
diagnostics to match the user's document, not my submissions."

*Answer.* `run` accepts arbitrary source; `session.needs_more_input(source) -> bool`
promotes the `stdin_source_needs_more*` family to a session query;
`RunOptions::{source_name, line_offset}` carries document identity so
diagnostics point at the host's lines (the mechanism
`run_source_with_line_offset` exists to serve — one of niu's two
`run_source*` calls is precisely the line-offset variant).

### 6.6 Lifecycle and environment deltas

*Need.* "Tell me when the working directory changes, when an exported
variable changes (so I can sync my own environment view), when the session
wants to exit, and let me decide startup files."

*Answer.* The §5.6 events (`cwd_changed`, `exported_variable_changed`,
`exit_requested`) plus the `RcPolicy` capability for profile/rc sourcing —
the engine stops assuming it owns startup, which is also what the rc
redesign (#359 plan A) needs from the boundary.

## 7. Stability tiers and version policy

### 7.1 Tiers

| Tier | Contents | Change policy |
| --- | --- | --- |
| **A — Stable** | `rubash_core::api` (Session, builder, options/outcome types, capability traits, events, diagnostics, error types) | Semver-strict. Breaking changes only at a major version; deprecations announced ≥1 minor before removal; every change via RFC (per RFC v1) |
| **B — Evolving** | driver helpers (`rubash-driver`), syntax surface (`parse`/AST-shaped views), usage printers | Semver, but deprecation may complete within the same minor series after one release of warning; changes noted in the API changelog |
| **C — Internal** | everything else currently `pub`: executor impl blocks, `shell::*`, `builtins::*`, bind registry, fd table, invocation plumbing | Explicitly unstable. Post-split these stop being `pub` outside their crate, or sit behind an `unstable-internals` feature with no promise. Existing consumers get a migration path (§8), not a freeze |

The tier of a type is visible from where it lives. A CI job diffs the tier-A
surface between releases (a public-API snapshot tool) and fails on
unannounced change — the mechanical half of the promise.

### 7.2 Versioning mechanics

- **Workspace lockstep through 1.5.x** (Q3): all four crates carry the
  product version; "rubash 1.5" is the contract name a host cites. The
  facade's version remains the release identity niubash's pin records.
- **The pin becomes honest.** Once tier A exists, niubash's `Cargo.toml`
  version requirement can state a real floor (`version = "1.5"`) and the
  release pin JSON remains only as the release-reproducibility mechanism it
  was designed as — not as the compatibility mechanism.
- **MSRV.** Today's `rust-version = "1.70"` becomes a commitment: MSRV is
  stated in the API docs, bumps are minor-version events announced in the
  changelog, never patch surprises.
- **API changelog.** A dedicated `docs/api/CHANGELOG.md` (or an API section
  in the main changelog) records every tier-A/B surface change per release,
  so a host upgrading can read one page and know its exposure.
- **Deprecation machinery.** `#[deprecated]` with a `since` and a migration
  note; tier-A removals only at majors; tier-B per its faster cadence
  above. Semantic behavior (the GNU-pinned semantics) is *not* versioned
  separately — a semantics fix is a bug fix at any tier, announced in the
  changelog, because hosts embedding a bash want bash.

## 8. Mapping: today's surface → the proposed tiers

| Today | Becomes | Tier |
| --- | --- | --- |
| `Executor::new` + scattered init | `Session::builder()…build()` | A |

## 9. niubash migration path

niubash is the baseline, so migration is a sequence the consumer can take
release by release without a flag day:

- **M-0 (pre-split): the census becomes a ledger.** The §3.2 table is
  checked into both repos as the API ledger; a pairing CI job (niubash
  built against rubash master — the arrangement that already exists via the
  `[patch]` sibling layout) runs on engine changes, so a vanished symbol
  fails the engine's CI, not the consumer's release. This step alone would
  have caught the lost-kill-hook incident before merge.
- **M-1 (split lands): facade parity.** The facade re-exports everything
  niu uses today; niu changes nothing and keeps building. Tier-C items niu
  touches are enumerated in the ledger with their target homes.
- **M-2: niu adopts the Session for its runtime.** `crates/niubash-runtime`'s
  shell/repl modules move their executor driving onto `Session` +
  capabilities (its history provider already matches). The 55 `set_env`
  sites collapse into builder initialization + the variables view.
- **M-3: tier-C exits, one family at a time.** kill hooks →
  `interrupt`/`inject_signal`; bind registry → the interactive layer's
  gated surface (or a promoted tier-B if the census justifies it);
  `invocation` plumbing → driver helpers; parser/lexer uses →
  `api::syntax`.
- **M-4: the version floor becomes real.** niu's requirement states the
  tier-A floor it actually needs; the release pin continues to pin exact
  revs for reproducibility, and the pairing job starts testing niu against
  the *oldest supported* engine minor as well as master.

## 11. Decisions (options + recommendation + ruling)

All eight questions were decided on **2026-10-25**: the owner approved this
RFC as written, adopting the recommendation recorded under each question.
Q4 and Q5 were named explicitly in the owner's ruling; the rest follow the
same approval. The recommendation text is kept verbatim under each
question, with the ruling appended.

- **Q1 — Execution model: synchronous or async signatures?**
  (a) Synchronous only. (b) Async-first. (c) Synchronous core, optional
  async wrapper in the driver crate.
  **Recommend (c), with (a) as the 1.5.0 deliverable.** Both real consumers
  drive synchronously today (niu's runtime calls the executor inline; the
  editor demo shape is a hosted thread per session). Async signatures would
  tax every signature in tier A for a consumer that does not exist yet; a
  driver-level wrapper can serve one later without reopening tier A.
  **Decided 2026-10-25: (c), with (a) as the 1.5.0 deliverable** —
  synchronous tier A; an async wrapper may be added in the driver crate
  later without reopening tier A.
- **Q2 — Events: one observer trait, or an event channel?**
  (a) The §5.6 observer trait. (b) An `mpsc`-style stream of event enums
  the host polls. (c) Both.
  **Recommend (a) for 1.5.0.** The observer matches how hosts already
  structure this (niu's runtime is a stateful object, not a poller), costs
  no allocation on the hot path, and default methods let the event set
  grow within a minor. (b) is a legitimate second front door if a host
  arrives whose runtime forbids callbacks; it can be layered over (a)
  without breaking it.
  **Decided 2026-10-25: (a)** — the §5.6 observer trait is the 1.5.0 event
  surface; a polled event channel may be layered over it later.
- **Q3 — Versioning: workspace lockstep or independent core semver?**
  (a) Lockstep: one version for all four crates. (b) `rubash-core` versions
  independently from the product.
  **Recommend (a) through 1.5.x, revisit at the next major.** With exactly
  one external consumer, independent versioning buys bookkeeping, not
  freedom — niu would still pin the pair that CI tested. Revisit when a
  second embedder needs core without the product's cadence.
  **Decided 2026-10-25: (a)** — workspace lockstep versioning through
  1.5.x; revisit at the next major.
- **Q4 — How much syntax surface do editor-class hosts get?**
  (a) None: parse is internal, hosts use `run` only. (b) A tier-B
  `api::syntax` module with owned view types (spans, node kinds) — shape
  may evolve under the tier-B cadence. (c) Freeze the internal `Ast` as
  tier A.
  **Recommend (b).** Editors legitimately need structure (highlighting,
  folding, diagnostics spans) and niu already consumes parser output for
  real features; but (c) would freeze the engine's internal data model —
  the single most expensive promise available — for a presentational need
  that owned view types serve.
  **Decided 2026-10-25: (b)** — the syntax surface is a tier-B
  `api::syntax` module of owned view types (spans, node kinds); the
  internal `Ast` is **not** frozen into tier A.
- **Q5 — Threading contract.**
  (a) `Session` is single-threaded (`!Send` by construction, documented).
  (b) Make `Session: Send` (replace `Rc<RefCell>` handles with
  `Arc<Mutex>` in capabilities).
  **Recommend (a) for 1.5.0, stated loudly.** It describes the engine as it
  is; hosts that need sessions on several threads create one per thread —
  which also matches the process-global arbitration rule in §5.1. (b) is a
  real cost imposed on every capability signature for a scenario no current
  consumer has.
  **Decided 2026-10-25: (a)** — the threading contract is explicitly
  single-threaded: one `Session` per thread, stated in the API docs and
  in the types (`!Send` by construction); hosts needing several threads
  create one session per thread, under the §5.1 arbitration rule for
  process-global resources.
- **Q6 — File-descriptor depth.**
  (a) Inject 0/1/2 only; the rest of the fd table stays internal.
  (b) Expose a host-implemented open-file table for all fds.
  **Recommend (a) for 1.5.0.** Hosts' demonstrated needs are the standard
  streams; a general fd table is a large contract (seekability, append
  semantics, device paths) with no consumer pressing on it yet. The
  builder's stream binding is shaped so (b) can be added as a capability
  later.
  **Decided 2026-10-25: (a)** — only fds 0/1/2 are injectable in 1.5.0;
  the rest of the fd table stays internal.
- **Q7 — Error types at the boundary.**
  (a) Re-export today's `ExecuteError` as tier A. (b) New
  `SessionError` / `ParseFailure` enums, `#[non_exhaustive]`, wrapping
  internal errors opaquely.
  **Recommend (b).** `ExecuteError` exposes internal variants; freezing it
  repeats the `ShellState` mistake in miniature. `#[non_exhaustive]` keeps
  the error surface growable within a minor.
  **Decided 2026-10-25: (b)** — new `SessionError` / `ParseFailure`
  enums, `#[non_exhaustive]`, wrapping internal errors opaquely;
  `ExecuteError` is not re-exported as tier A.
- **Q8 — Cancellation semantics.**
  (a) Cooperative flag only (`interrupt`). (b) Signal injection only.
  (c) Both, as §6.4.
  **Recommend (c).** They answer different host intents (a UI cancel vs.
  faithful signal parity, including trap behavior), and both map onto
  machinery that exists; offering only one forces hosts to misuse the
  other.
  **Decided 2026-10-25: (c)** — both mechanisms ship, as §6.4: the
  cooperative `interrupt()` and faithful `inject_signal(sig)`.
- **Carried from RFC v1, not re-decided here:** the debugger decision
  points (handled by the sibling debugger design) and the pre-install
  bundle question (owner's, unrelated to the API). The #359 plan-A decision
  is assumed as the rc-policy capability's data model (§5.5); if plan A
  changes, only that capability's shape changes, not the layering.
